# 架构决策

## 2026-11-14：灵兔 AI 名称与持久化身份分离

用户要求统一改名为“灵兔 AI”。界面、图中文字、窗口/网页、后台、npm 包名、安装程序与云端产物使用新名称；历史来源与发布证据保留原名。npm/productName 变化会影响 Electron 默认 userData，因此 main 在单实例锁前显式定位旧目录，并保留显式隔离参数；安装 appId、IPC 契约与登录分区暂不改动，避免丢失已有数据或并存安装身份。未提供正式官网地址时不沿用原产品官网。改动仅本机，不提交或发布，详见 BRANDING.md。

## 2026-11-14：独立主项目根与构建、发布分开

用户确认主目录为 F:\Setupgod\yunduo-ui，其他工作区保持原样。当前目录结构已满足客户端/服务端/固定运行时分离，因此不为整理而移动业务代码或运行数据；新增 PROJECT_LAYOUT.md 统一维护入口，修订旧仓库和过时能力描述。云端工作流收回 .github，按项目位于仓库根的结构执行，不沿用被取消分支。默认内容权限只读，只生成 Actions Artifacts；公开发布需另行授权，避免再次上传或发布到错误仓库。本轮仅本机改动，不初始化 Git、设远程、提交或推送。旧验证和发布文档明确标记为历史，保留追溯。

## 2026-11-13：服务端独立导入，保留默认本机模式

用户要求将 PR #21 合并进云朵并自行测试，因此只将服务端覆盖层和原生管理网页放入 server，不用上游 React 桌面覆盖 Vue。默认 local 保持既有资料，托管通过已有受限设备会话协议接入；模式、服务或账号变化后停 AI 并重启以切换工作区。未验证身份不展示或操作旧账号资料，平台分区也按工作区隔离。供应商 Key 留在服务端，桌面只系统加密保存受限会话；实际托管 HTTP 提交证据经 traceId 本机转发记录。原生源码保留固定来源/哈希/许可，自有工具 verify.ts 单独做 TS 与 lint，服务端另跑 Go/原生网页验证。详细边界见 MANAGED_SERVICE.md。

## 2026-11-13：模拟店铺验收加一层 CDP 真机驱动，无口令访问给说明页

用户要求验收是真点出来的，而不是测试桩里的断言。原有 `npm run test:desktop` 在窗口工厂内用 `executeJavaScript` 核对状态，能证明数据流，但不能证明按钮真的可点、顾客页在真实浏览器里真的渲染。因此新增 `scripts/cdp-verify.mjs`（`npm run verify:cdp`）：以 `--remote-debugging-port` 起真实 Electron 窗口、以真实 Microsoft Edge 打开模拟顾客页，全程只用 CDP 的点击、输入、截图，不注入任何业务桩，也不连平台。它不被计入 `npm run check`：会开真实窗口、占用 5173/9222/9333/43100、依赖本机 Edge，不适合无头或 CI 环境；桌面 smoke 仍是每次改动必跑的那一层。

脚本先执行 `build:desktop`：Electron 主进程加载的是打包后的 `dist-electron`，只改 `electron/` 源码不重打包，验证到的仍是旧产物（本轮就因此先看到旧版纯文本拒绝页）。每次运行使用临时 `--user-data-dir` 与临时浏览器资料目录，跑完即删，不碰 `%APPDATA%` 里的日常数据，也不在真实店铺里留下痕迹。

无口令打开顾客页改为返回 403 的 HTML 说明页（指引回桌面端重开、页内不出现对方给的口令、也没有重试入口），而不是一行纯文本：这条链接会被复制、收藏、刷新，纯文本会让人以为页面坏了。拒绝权仍只在桌面端：口令错、口令缺失、口令过期对外表现一致，`/api/*` 依旧是 401 JSON。可进入性没有放宽，只是把“打不开”讲清楚。

## 2026-11-12：恢复已归档聊天上下文

用户的实际请求日志证明模型仅收到最后一句。原因是上游历史 HTTP 不可用时只剩队列批次，已有归档未参与生成。生产注入 TypeScript 组装器，按店铺和买家读取最新归档，合并平台历史与当前消息，取消生成前的 20 条截断，再由既有 16K/8K 机制控制长度。相比仅增大平台接口 limit，这种方案能在接口不可用时继续使用已经采集的聊天；不尝试猜测平台未返回的记录。

此决策替代本日早期“保持最近 20 条窗口”的限制，不改变归档最多 100 条和 200 会话的现有持久化边界，不缓存跨会话摘要，不将未批准候选放入历史。后续若需更早记录，应先确认平台历史契约与数据保留策略，再实现分页采集并独立验收。

## 2026-11-12：逐条消息解释未调用 AI 与开放回复间隔

用户要求在买家消息上看到是否调用 AI 及未调用原因，并能调整 60 秒间隔。新增有界证据跟踪，区分采集、调度、准备、真实 HTTP 发起、正文完成及发送确认；不恢复限流刷屏，不从现有开关推断历史事实。只读 worker 观测限于主进程，不暴露运行时对象。

修正新消息使旧候选失效后仍永久人工暂停的路径，保留显式取消与人工接管。间隔通过独立表单及受限配置适配修改，默认值保持 60，0 可关闭，不代替其他安全检查。

## 2026-11-12：去除轮询噪声并计量 AI 回复耗时

按用户要求不保存高频 reply:throttled 轮询记录，而非仅在 UI 隐藏；限流与真实异常保留。计时从模型生成入口而非买家消息时间开始，到正文完成为止；使用单调时钟，包含准备和压缩，排除人工确认与平台发送，避免将人等了多久混入模型耗时。摘要回合单独标示以便定位时间来源。

## 2026-11-12：确认后逐字输入再发送

按用户要求将整段填入改为逐个可见字符追加，默认 50ms，仍是网页内操作，不使用系统键盘或系统鼠标。保持明确批准，完成输入后才点击发送；取消信号、买家变化、网页新消息和人工编辑均阻断。采用字素分割以避免组合 emoji 被拆开。输入中止保留草稿供人工核对，不自动删除用户内容。

## 2026-11-12：发送确认区分新消息与历史不可读

用户实测确认后反复提示“已有新消息或无法核对历史”。审查发现原确认依赖可能不可用的私有历史 HTTP 请求，并跨来源强比较消息 ID/时间。改为生成前采集网页基线、确认时定位同一买家核对有序正文及媒体，绑定页面实例；元数据补全不作新增。读取暂时失败保留候选，不让用户不断重新生成并支付模型费用；不移除真实新消息、人工回复和停店检查。

## 2026-11-12：16K 触发并压至约 8K

采用同模型语义摘要，更早对话和检索资料压缩，系统规则、近期原文和图像输入保持；失败时停止，不以丢弃受保护资料或发送原超限请求兜底。每请求独立计算，避免摘要缓存跨店或在规则修改后过期。原先保持的 20 条窗口已由本页“恢复已归档聊天上下文”决策替代，不声称拿到了未采集的平台历史。

选择 js-tiktoken 1.0.21 lite 的本地 cl100k_base 作为统一计量口径，按 16,384/8,192 执行；跨供应商和图片 token 存在差异，界面明确标注估算。摘要调用会增加费用，自动测试仅使用本机夹具。摘要及最终请求分开记录，正式发送审批不变。

## 2026-11-12：拼多多采用网页按钮发送

用户明确要求浏览器内置操控式点击，不操作系统鼠标。查明上游当前 PddWebAdapter 实际发送路径为浏览器原生回车事件，因此在本工程 TypeScript 装配层替换文字发送策略，复用已有 DOM hook，并收紧为按钮单击、不补回车、完整正文校验及真实回显核对。原上游适配器默认行为保留，其他平台不受影响。

由于上游注明平台可能拒绝脚本 click，实际采用 DOM 定位按钮后通过浏览器内部鼠标事件触发可信点击，不移动系统指针；守卫验证买家、正文、目标按钮及操作令牌。不发送回车。离线夹具仅验证接线和防重复行为，实店可用性单独验收。

## 2026-11-12：实时调试及逐条批准 AI 回复

按用户要求使用独立原生日志窗，避免店铺 WebContentsView 覆盖 HTML 弹层。通过主进程内存记录已采集消息和实际模型 messages，不读取 HTTP 凭证、不新增敏感上下文落盘。固定容量与截断说明保证长时运行不会无限增长。

确认门位于原引擎统一发送入口、欢迎语处理之后，复用发送节奏、台账和不确定结果隔离。没有选用“生成后转成人工 send-reply”方式，因为那会绕过原引擎台账并容易重复发送。每条候选只能批准一次；拒绝、过期或上下文改变不发送，启动不恢复任何批准状态。自动超时兜底停用，转人工提示亦经确认。

## 2026-11-13：通用话术作为表达参考接入

将用户要求整理的 80 条人工通用改写作为静态库共用于快捷回复与模型上下文，原始 FAQ/规则与候选不导入。当前问题文字最多召回 3 条，在既有 prepareModelContext 装配点先附加来源用途、事实边界与适用条件，再进入原 16K/8K 压缩器；不修改 vendor，不新增模型调用或改变发送门。静态示例受系统预算保护，买家文字不放入该块。复制只开放可信窗口按已知话术 ID 写剪贴板，不开放读取或任意写入。相关维护与限制见 GENERIC_PHRASES.md。

旧 CSS 和 data-v 标记保留，修复明确语法问题；逐模块有截图证据后再移除。避免目录迁移与全量视觉重写同时发生。

## 2026-11-13：本机模拟店铺复用真实回复链路

用户要求“添加店铺里加模拟店铺、做一个仿照的客服聊天、再开一个端口开网页模拟不同顾客”。实现选择复用上游真实链路：新增平台 id sim-local 走能力注入点进入白名单，模拟店铺有自己的 TS 适配器与门店管理器，顾客消息经本地回环 HTTP 页进入 SimHub，再由上游既有 ingest → 采集监控 → 会话快照 → 回复引擎 → 逐条确认门 → send-reply → 适配器 sendText 走完；客服回复仍在桌面端由人确认后发出。

不采用另写一套“演示聊天界面 + 假发送”的做法：那样会绕过统一确认门，界面看起来能发消息却不代表任何真实发送，也无法验证采集、会话归档、AI 候选与确认流程是否真的接通。代价是必须给第三方后端加一个只有本工程使用的最小注入点（合计 4 处赋值），该补丁已在 vendor/PROVENANCE.md 与 source-files.json 登记，未注入时上游行为不变。

模拟能力只在桌面版存在：浏览器预览的 emptySnapshot 不包含 sim-local，添加店铺里也就不会出现该选项，不伪造可选。诚实边界固定为——界面与页面都标注“本机模拟、不连接真实平台”，模拟顾客页没有登录态，回复成功只代表写进本机记录，不声称真实买家收到。一次运行一次性回环口令放在主进程内存与用户复制的那条链接里，页面不带任何外部资源。
