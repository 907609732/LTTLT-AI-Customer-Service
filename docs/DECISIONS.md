# 架构决策

## 2026-11-19：尺码终态只校验不重写；本机视觉独立但托管旁路

尺码问题在 vendor 禁用词/店铺长度处理之后只能做终态校验：以 guard 生成时 canonical 为基准，只在内存中用占位保护 eligible 标签并调用真实 vendor 过滤器，实际 final 必须等于期望或为其长度前缀。任意标签替换（含 2XL/3XL/加大码/中文自定义码）拒绝；普通非标签删除和店铺截断允许；不重写 final text、不重插禁词、占位不进入真实消息。canonical 由守卫在 `enforceSizeReply` 之后用 guarded 结果自身的真实 traceId 回调候选 guard（vendor 早于守卫的 raw result 不捕获）；训练在 AsyncLocalStorage owner 内取。valid selection 缺 canonical 直接闭锁，不再用旧正则兜底。正式欢迎前缀仅在当前 welcome 版本与提案版本一致时，按可信 greeting + 换行精确剥离，不猜任意第一行。知识库试问也走同一尺码证据和版本复核，但保留原 resolution/租约/预算且不发送。候选按 reply trace 有界保存 `evidence|null`：明确无尺码记为 null 并保持普通回复，unknown/被淘汰的 AI trace 闭锁；训练/试问 trace 不占正式回复候选。

本机图片模型独立保存在 `vision-model.json`，Key 只走 safeStorage；公共 assembly 在 `onKnowledgeModel` 包装知识端口。`inherit` 继续原能力，`custom` 只在当前配置通过图片验证后分流知识图片；managed 在最早分支直接回调原端口，不读取本机视觉 generation。损坏本机视觉文件只关闭图片，不阻断文字和启动；命令 probe/verify 必须带 expected revision。买家图片回复保持原路径。

## 2026-11-18：回复监控会话用只读投影，商品不猜测

用户要求监控显示当前会话的买/卖消息和当前咨询商品，同时明确候选与真实已发送。决定不把编辑、删除或质检塞进小窗，也不让前端自行发送；复用现有 snapshot、`ReviewConsole` 和统一确认门，新增纯函数投影按 `storeId + uid` 精确匹配会话，系统/未知来源保持中立。候选按 pending/sending/failed/sent 分型，已发送优先采用真实卖家回显，避免重复。

商品只沿真实生成 trace 的 `reviewContext.productId/goodsTitle` 最小投影；候选只复制同店同买家 trace。标题/图片由主进程按同店精确 productId 查询已有知识绑定或平台详情，优先现成 HTTPS 图；无资料时显示编号/平台标题或“未识别”。不从模型正文、推荐商品、商品目录或跨店/跨买家数据补全。代价是商品资料未采集时只能显示有限信息，监控也不承诺实时页面商品；换商品的识别仍依赖下一次真实生成上下文。详见 [REPLY_MONITOR.md](REPLY_MONITOR.md)。

## 2026-11-18：源码调试放进唯一监控子窗，owner/打包 gate 在主进程

用户要求把右上回复监控移到左下，并在同一窗口提供 GM 与真实交互 CMD，打包版完全不需要。决定保留 340×300 紧凑单例子窗，源码底栏按需展开 960×620；不新增第二窗口，也不做全局置顶。GM 使用固定注册表而非 eval；CMD 使用 node-pty/ConPTY，xterm 只在首次进入 CMD 标签异步加载，避免日常监控承担终端开销。所有请求以当前监控窗口的服务主 frame、实际 owner WebContents 和 workspace 三重绑定；关闭/切换工作区杀进程树，旧宿主回调绑定旧 owner。

打包 gate 以 `app.isPackaged` 为主进程唯一权威：不创建 controller、不注册 IPC；普通 preload 编译时固定关闭调试桥，监控专用的 `developer-preload.cjs` 只在源码窗口选择且不进入 electron-builder 白名单。没有环境变量/命令行开关。PDD 弹窗策略只在内存按店记录，复用厂家 `webContentsOf(storeId)` 的实际 WebContents 并核对 `mms.pinduoduo.com`；Electron WebContentsView 的 `BrowserWindow.fromWebContents` 会返回父窗口，不能按 null 判断内嵌页。代价是源码监控需要单独 native preload 构建和 node-pty 原生验证，且调试窗口关闭后不恢复 shell；真实 PDD 页面仍需另行实店验收。

## 2026-11-17：托管接待知识预算在 resolver 之后按 token 整条填充

管理员的 `retrieval_budget` / `retrieval_order` 只控制已审核候选的预算填充，不参与冲突胜出。决定先复用 `repo.resolveKnowledge`（托管候选窗口 50 条 / 60,000 字符）确定审核、范围、SKU 覆盖、有效期和命中顺序，再按 binding 固定最前、template 固定最后、store/canonical 可交换的顺序选取完整 citation。预算按现有 cl100k tokenizer 对序列化 citation 在独立 worker 中批量计量，不按字符估算，也不在主线程处理病态 Unicode。超预算整条省略，并与 resolver omitted 合并计数。

代价与边界：托管接待最多加载 50 条完整引用并多一次 worker 计量；预算只覆盖引用载荷，不含系统提示与对话。本机 Key、策略停用、旧服务端缺字段或读取失败回退既有 10 条 / 24,000 字符路径，不用本地默认策略伪造服务端启用；16K/8K 压缩和统一发送确认门不变。
