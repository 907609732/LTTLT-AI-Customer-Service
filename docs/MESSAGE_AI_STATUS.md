# 买家消息是否交给 AI：诊断与回复间隔

## 界面

每条“买家消息”下显示本次运行观测到的处理状态与原因：尚未调度、店铺/全局 AI 未开、暂停/人工接管、等待回复间隔、店铺分钟上限、并发等待、准备上下文、已发起模型请求、生成完成、等待人工确认、逐字发送、已发送、失败或取消。可从有对应 trace 的消息跳到实际 AI 请求；会话暂停提供显式恢复入口。

“已发起 AI 请求”必须有实际调用 fetch 的证据，仅组装 messages 或进入引擎不算。该标记说明本机发起 HTTP 尝试，不保证网络成功或服务端收到；失败原因继续显示。摘要压缩调用与正式回复分别处理，不能把“发了摘要”写成“正式回复已交给 AI”。失败前若已发起请求，事实不会被后续排队事件改为未调用。

状态原地更新，不把 reply:throttled 轮询重新追加为日志。相同买家的多条消息用消息 ID、原始正文指纹和时间关联；不同真实 ID 的相同文字不能互相冒用调用证据。跨采集源的合成 ID 才允许正文及短时间窗匹配。证据和日志均有界，仅保留本次运行；历史归档没有对应运行证据时显示未知，不用当前开关猜测过去是否调用。

## 设置：AI 回复间隔

左下角“设置” → “AI 回复间隔” → “同一买家两次回复至少间隔（秒）”。显示当前保存值，默认 60，支持 0～3600 整数秒。0 取消该间隔；每店分钟上限、逐条人工确认和其他安全保护保持。

间隔从上次发送计起，在引擎调用模型前就可能让新消息等待，所以“采集到买家消息”不等于“立即发给 AI”。保存即影响后续调度及发送复核，无需重新保存 Key，不产生模型调用，不自动启用 AI；按旧值校验防止并发覆盖。对应配置为 reply.perUidMinIntervalMs，UI 使用秒，持久化使用毫秒。不要通过改变默认值来掩盖会话被人工接管或队列未消费的问题。

## 本轮查明及修正

本机配置确有同一买家 60 秒间隔。另复现旧候选因买家新消息作废后，原统一确认门把所有拒绝结果都当作 review 人工接管，导致后续买家消息持续被跳过。现区分新消息替代与用户主动取消：新消息替代不永久暂停，旧认领归还队列后处理最新消息，仍需对新候选确认；用户主动取消、超时无操作、真实人工接管和异常核对仍保留原暂停策略。

还会如实解释消息超过处理时效/重连补回窗口、人工已回复、不需要重复回复、命中转人工关键词、识图/压缩/鉴权失败等分支。没有消费或请求证据时只显示“队列状态待排查”，不能编造已丢消息或已请求模型。

## 实现入口

- electron/message-diagnostics.ts：逐条关联、状态推断、缓存去重及有界清理；读取真实 worker 状态仅在主进程。
- electron/review-console.ts：将状态附在买家消息 LogEntry.ai；真实提交、生成、确认、发送的 trace/事件推进状态。
- reply-engine 最小注入：各调度/跳过分支给出带原消息引用的 decision 事件；新消息替代不留下 review 永久暂停。
- ai-client 最小注入：校验地址/凭据后，在调用 fetch 前发出 submitted 事件，不再把 request 准备事件当已提交。
- SettingsView / REPLY_PACING：间隔表单与现有 config.update 白名单适配，不新增任意配置能力。

本轮不读取或展示密钥，不增加平台探测请求，不自动点击真实买家的确认。验收覆盖状态原因、跨消息隔离、正式请求证据、候选替代回归、间隔保存/重启及越界/并发旧值拒绝。
