# 上下文压缩：16K 触发，目标 8K

本机运行时默认启用。每次正式生成回复或训练前，对已经组装的完整 messages 计量：估算输入达到 16,384 token 时触发，压缩后的正式回复输入不超过约 8,192 token。未达到阈值保持原文，不额外调用模型，不为凑到 8K 补充无用文字。

## 内容与请求流程

内置通用表达若命中，由 generic-phrases.ts 在进入压缩器前插入最多 3 条静态示例及边界，属于实际系统输入，计入 beforeTokens 与最终 afterTokens 并保留。买家查询不插入系统块；没有匹配不改变上下文。该参考不提供商品事实或执行证据，见 GENERIC_PHRASES.md。

1. 生产引擎先合并同一 storeId + uid 的本机会话归档（当前最多 100 条）、平台成功读取的历史及本轮消息，去重并按时间排序；不再提前截成 20 条。买家和实际已发送的客服回复一起参与计量，尚未批准的 AI 候选不属于聊天历史。平台历史接口不可用时仍读取本机归档；软件从未采集到的更早记录无法补全，不能宣称拿到了平台全部历史。
2. 完整保留系统消息和所有实际图片输入，优先保留最近 4 条原始消息。预算紧张时保留最后买家诉求、最后客服回复及最新消息，按时间排列。
3. 更早对话和检索资料由当前配置的同一个模型整理成中文事实摘要，要求保留商品/订单编号、金额单位、已承诺及未解决事项、不确定性，不得新增承诺。该步骤额外产生一次模型调用和费用，不会向买家发送消息。
4. 正式请求包含原系统消息、注明为不可信数据的摘要、受保护近期原文和图片。摘要不能覆盖系统规则。AI 回复仍逐条经用户确认后才允许点击网页发送。
5. 服务商若超出摘要输出预算，本地再收紧摘要，日志明确标记可能有遗漏。系统、近期原文和图片本身已占满预算时，拒绝请求并提示调整，不能偷偷裁剪这些内容来宣称压缩成功。

摘要失败不回退发送原始超限请求。真实接待的该会话转入人工核对，防止队列自动重复产生摘要费用；训练场显示失败。任务停止或服务关闭后不继续发起最终回复请求。每次请求独立压缩，不缓存或混用不同店铺/买家的摘要；修改规则后重新计算。

## Token 口径

主进程使用锁定的 js-tiktoken 1.0.21 lite 和内置 cl100k_base 词表，文本按 BPE 分词计算，并计入消息框架开销。特殊 token 字样作为普通资料，不按控制指令处理。词表随包分发，不从 CDN 下载，不进入 Vue 渲染包。

自定义服务商可能采用不同 tokenizer。图片真实 token 取决于模型、尺寸和分辨率，当前无法从 URL 判断，因此每图预留 1,536 token，不将 URL 字符数当图像 token。阈值与目标是本项目统一估算口径，不能保证与服务商 usage 或账单完全相等；不包含生成输出 token。用户选择的模型仍需接受压缩时的原始输入长度及约定的摘要输出预算。

## 日志与维护

日志 → AI 上下文调试区区分“上下文摘要”和“回复生成”。可查看摘要请求和模型结果、正式实际 messages、压缩前后估算值、计量方式、保留原始条数、实际使用摘要以及是否被收紧。关闭或重启仍沿用有界内存策略，不新增摘要落盘，不记录请求头或密钥。摘要是模型生成的有损资料，需要结合近期原文及人工确认核对。

入口为 electron/context-compression.ts，阈值常量集中定义；local-runtime 注入到上游 AiClient 的 prepareContext，发生在最终 wire trace 与请求之前。上游只保留可选注入及摘要 maxTokens 覆盖点，默认未注入时不压缩。trace 用于调试的摘要回合不能关联为待发送买家回复。

变更必须验证：16K 下不压缩、恰到阈值触发、压后不超过 8K、系统与近期原文/图片保留、长摘要收紧、失败不发送超限请求、取消不继续生成、实际 HTTP 正文与最终日志一致，以及发送确认不被绕过。单元与桌面验证都使用合成资料及本机模型夹具。
